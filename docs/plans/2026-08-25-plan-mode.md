# Metis Plan Mode Implementation Plan

> **For implementers:** Implement this plan task-by-task, in order. Steps use checkbox (`- [ ]`) syntax for tracking; check each box as it's completed.

**Goal:** Add a first-class Plan collaboration mode to Metis that lets the model inspect and ask questions without changing the project, submit a durable structured plan, and let the user revise, cancel, preview, or start that plan from the chat UI.

**Architecture:** Keep the immutable session appearance (`chat` or `code`) separate from a durable collaboration mode (`default` or `plan`). Store mode changes and complete plan revisions as JSONL session-control records, exclude those controls and historical `submit_plan` calls from normal provider context, and project plan proposals through the existing `ItemView`/`item/completed` path. Enforce Plan safety in the tool registry, permission boundary, and workspace sandbox; the prompt describes behavior but is not the security boundary.

**Tech Stack:** Node.js 22.19+, TypeScript 5.9, TypeBox 1.1, Vitest 4.1, Electron 43, React 19, i18next, existing `@anthropic-ai/sandbox-runtime`, npm workspaces.

**Spec:** `docs/plans/2026-08-25-plan-mode.md#agreed-product-contract`

## Global Constraints

- Keep `AgentMode = "chat" | "code"` unchanged; Plan is an orthogonal collaboration mode available to primary interactive Chat and Code sessions.
- Do not expose Plan mode in scheduled sessions or subagent sessions in the MVP.
- Inject the Plan-specific system prompt and expose `submit_plan` only while the effective collaboration mode is `plan`.
- Never parse `<proposed_plan>` or any other free-form output tag as the authoritative submission path.
- In Plan mode, model-visible tools are limited to trusted read/exploration tools: built-in `read`, `grep`, `bash`, `web_fetch`, optionally configured built-in `web_search` and `describe_image`, trusted host `ask_user`, and built-in `submit_plan`.
- Do not expose `edit`, `write`, `set_tasks`, goal mutation tools, extension tools, MCP tools, subagent tools, or unknown custom tools in Plan mode.
- Plan Bash always executes in the existing workspace sandbox with every workspace root read-only; commands classified as sensitive, unknown/opaque, networked, elevated, destructive, or externally mutating are denied, and no approval path can promote execution to the host.
- If the Plan sandbox cannot initialize, fail closed; never fall back to host Bash.
- Metis-owned session work/temp directories may remain writable for command output and temporary files; project/workspace roots may not.
- `submit_plan.title` is 1-256 UTF-16 code units with no control characters; `submit_plan.markdown` is 1-65,536 UTF-8 bytes.
- Snapshot and `session/readItems` pages must stop before 6 MiB of serialized item payload so many valid Plan revisions cannot exceed the existing 8 MiB protocol envelope.
- A new plan revision is a complete replacement, not a patch; older revisions remain durable and render as `superseded`.
- JSONL session controls are the only canonical Plan persistence in the MVP; do not create a second Markdown plan file automatically.
- Persistence is not context inclusion: only the latest current proposal is injected while revising, and only the exact accepted revision is injected during its execution turn.
- Starting execution changes collaboration mode to `default` before the provider request, restores the configured normal tools, and keeps `set_tasks` as the separate execution-progress mechanism.
- The plan card body has a fixed 280 px viewport with internal scrolling; its actions are Start execution, Cancel, Open, and Revise plan.
- Revise plan uses the existing composer with a removable context chip and free-form user text; do not add a modal plan editor.
- Reuse existing protocol validation, JSONL journal, `ItemView`, `item/completed`, projection reducer, Markdown renderer, tools sidebar, IPC bridge, and sandbox runtime. Add no dependency.
- Bump the coding-agent session version from 11 to 12 and the App Protocol version from 20 to 21.
- This handoff plan is tracked only because the user explicitly requested remote delivery. During implementation, keep checkbox/progress edits to `docs/plans/2026-08-25-plan-mode.md` unstaged and exclude them from functional commits unless the user explicitly asks otherwise.

## Agreed Product Contract

### User flow

1. The user opens an existing primary Chat or Code task and switches the collaboration control from Default to Plan.
2. Metis durably records `plan`, rebuilds the prompt, projects the configured tool list down to the Plan-safe set, and refreshes the Bash sandbox boundary.
3. The model explores with reads, searches, read-only Bash, and `ask_user`. Project changes are blocked independently of what the model says.
4. When the model has a decision-complete plan, it calls `submit_plan({ title, markdown })`. Metis validates and appends a complete proposal control record.
5. The chat transcript renders that control record as a fixed-height plan card. Raw `submit_plan` tool-call/result plumbing is not rendered as an extra tool step.
6. Open shows the same Markdown in the existing right tools sidebar. Revise focuses the existing composer and adds a chip identifying the current revision; the user's ordinary message asks for changes, and the next `submit_plan` call creates a complete replacement revision.
7. Cancel marks the exact proposal cancelled, returns to Default, and does not run the model.
8. Start execution durably identifies the exact plan revision, starts a normal runtime turn, marks the plan accepted, switches to Default before provider work, injects that accepted plan only for the execution turn, and exposes normal tools.

### State and context rules

- `session_collaboration_mode` is session-global journal state with a default fallback of `default`.
- `session_plan_proposal` stores `planId`, `revision`, `title`, and complete `markdown`; its control-entry `id`, `parentId`, and `timestamp` provide item identity, branch attachment, and chronology.
- `session_plan_status` records `accepted` or `cancelled` for an exact `planId`/`revision`.
- A later proposal with the same `planId` and `revision + 1` derives the prior proposal's public status as `superseded`.
- Session controls never advance the transcript leaf and are excluded from `SessionManager.getEntries()` and `buildSessionContext()`.
- Before each provider request, Metis removes historical `submit_plan` assistant tool-call blocks and matching tool-result messages. It then appends at most one hidden `metis_plan_context` custom message for the latest proposal or the accepted execution revision.
- Switching back to Default therefore removes both the current `submit_plan` definition and historical evidence that could make a model believe the tool is still callable.

### Failure behavior

- A stale card action returns `CONFLICT`; an active turn or pending interaction returns `BUSY`; scheduled/subagent sessions return the existing read-only/not-found style error used by their host boundary.
- A model that never calls `submit_plan` produces no plan card. The user can continue prompting in Plan mode or cancel; there is no fallback tag parser.
- Plan Bash commands that try to write fail at the filesystem sandbox. Bash commands classified as sensitive-read, unknown, network, elevation, destructive, or external-side-effect are denied before execution without asking for approval; sensitive files remain available only through the existing structured-read permission path.
- A sandbox startup error is surfaced as a tool error and keeps the workspace unchanged.
- A provider/runtime failure after Start may interrupt the execution turn, but the selected revision remains accepted and auditable; starting a new Plan produces a new `planId`.

| Term | Exact meaning |
|---|---|
| Configured tools | The complete normal tool-name selection that must survive mode changes and registry reloads. |

## Why This Architecture Is Deliberate

Do not replace these decisions during implementation unless the user changes the product contract:

| Decision | Reason | Rejected alternative |
|---|---|---|
| Use a structured `submit_plan` tool. | Metis supports models with different output habits; host schema validation and a real tool call are more reliable than parsing prose. | Parsing `<proposed_plan>` or another model-emitted tag. |
| Keep Plan orthogonal to Chat/Code. | Chat/Code appearance and Plan collaboration behavior change for different reasons and have different lifecycles. | Adding a third `AgentMode` value and migrating every appearance branch. |
| Store complete revisions as JSONL controls. | The existing append-only journal supplies durability, ordering, branch attachment, migration, and restart recovery. | Storing only the latest plan, mutating an old record, or creating an unrelated database. |
| Exclude Plan controls from ordinary context. | Persistence must not imply that every revision consumes provider context. | Serializing the whole JSONL history into every request. |
| Inject at most one selected revision. | Revision requests need the latest proposal; execution needs the exact accepted proposal; all other turns need none. | Letting historical `submit_plan` calls/results accumulate in the prompt. |
| Reuse `ItemView` and `item/completed`. | Existing pagination, reconnect, replacement-by-item-ID, transcript virtualization, and event handling already solve delivery. | Creating a separate Plan event stream and second renderer collection. |
| Use a composer chip for revision. | It reuses the normal user-message loop and keeps the model responsible for producing a complete replacement. | A second modal editor or client-side Markdown patch format. |
| Keep JSONL as the only automatic Plan file. | One canonical copy avoids drift, naming ambiguity, cleanup, and accidental repository changes. | Automatically writing `docs/plans/<title>.md` or another Markdown copy. |
| Enforce safety in tools, permission routing, and sandbox mounts. | A prompt is behavioral guidance and cannot be the authorization boundary. | Merely telling the model not to write. |
| Restore Default before execution provider work. | The accepted turn needs normal edit/write/task tools, while the planning turn must never receive them. | Leaving Plan mode active and selectively approving writes. |
| Keep `set_tasks` for execution progress. | Proposal content and implementation progress are different state with different consumers. | Treating the Plan card itself as mutable task progress. |

### Explicit MVP non-goals

- Selecting Plan before the first session is created on `NewTaskHome`.
- Plan mode in scheduled sessions or subagent sessions.
- Extension/MCP/custom tools in Plan, even when annotated read-only.
- A fallback tag parser for models that do not call `submit_plan`.
- Partial Plan patches, visual revision diffs, collaborative editing, or merging concurrent revisions.
- Automatic Plan Markdown export or repository file creation.
- A dedicated full-screen editor; Open uses the existing tools sidebar.
- Replacing the existing execution task/progress system.

## End-to-End Ownership and Data Flow

The same Plan content crosses several boundaries, but each boundary owns a different representation:

```text
model submit_plan({ title, markdown })
  -> AgentSession trusted tool definition
  -> SessionManager appends session_plan_proposal to JSONL
  -> reducePlanState() derives StoredPlan + public status
  -> AgentSession emits plan_changed(entryIds)
  -> App Server projects the proposal as ItemView { content: [{ type: "plan" }] }
  -> existing item/completed event or snapshot/readItems page
  -> Desktop projection reducer stores the ordinary item
  -> Transcript renders PlanCard; ToolsSidebar can render PlanPreview

Before a provider request only:
JSONL controls + durable execution scope
  -> projectPlanContext()
  -> zero or one hidden metis_plan_context JSON message
  -> provider request
```

Ownership rules:

| Layer | Owns | Must not own |
|---|---|---|
| SessionManager | Validated append-only mode/proposal/status records and pure reduced Plan state. | UI state, provider tool schemas, or App Protocol views. |
| AgentSession | Effective prompt/tools, trusted `submit_plan`, provider-context projection, permission enforcement, and execution transition. | Desktop cards or duplicate persistence. |
| App Protocol | Strict public request/result/event/view shapes. | Business-state reduction or filesystem policy. |
| App Server | Session-class/idle/stale validation, durable operation routing, journal projection, event publication, and page-size budgeting. | Parsing model prose or storing a second Plan copy. |
| Desktop | RPC invocation, projection state, pending-button state, Plan card/preview/chip interactions. | Authoritative status transitions or optimistic Plan records. |

The UI is projection-driven. It may show a local pending spinner/disabled button, but collaboration mode, Plan status, revision, and Markdown always come back from App Server snapshots/events.

## Durable State Machine

Collaboration mode and proposal status are separate axes. `revising` is not a durable status; it is only a composer chip while the session remains `plan` with a `proposed` current revision.

| Effective state | Allowed user action | Durable write | Provider turn? | Result |
|---|---|---|---|---|
| `default`, no current proposal | Enter Plan | Append `session_collaboration_mode(plan)` | No | Plan prompt/tools/sandbox boundary become effective. |
| `plan`, no current proposal | Send exploration request | Normal user/assistant/tool transcript entries | Yes, Plan-safe | Model may inspect, ask, or eventually call `submit_plan`. |
| `plan`, no current proposal | Return to Default | Append `session_collaboration_mode(default)` | No | Normal configured tools/prompt are restored. |
| `plan`, current `proposed` | Open | None | No | Existing sidebar opens the exact revision. |
| `plan`, current `proposed` | Revise | Normal user message only; later tool call appends next proposal | Yes, Plan-safe | Same `planId`, `revision + 1`; old revision derives `superseded`. |
| `plan`, current `proposed` | Cancel | Append exact `session_plan_status(cancelled)`, then mode `default` | No | Card becomes cancelled; normal mode returns. |
| `plan`, current `proposed` | Start | Admit durable prompt with exact ref; append `accepted`, then mode `default` | Yes, Default tools | Accepted revision is injected for this execution operation only. |
| `default`, accepted/cancelled history only | Enter Plan again | Append mode `plan` | No | The next proposal gets a new `planId` and revision 1. |

Derived status rules, in priority order:

1. An exact terminal status control makes that proposal `accepted` or `cancelled`.
2. Otherwise, a later branch-visible proposal with the same `planId` and a higher revision makes it `superseded`.
3. Otherwise, it is `proposed` and may be the current proposal.
4. `currentPlan` is the latest branch-visible proposal still derived as `proposed`.
5. Mode controls are session-global; proposal/status controls are reduced against the active branch IDs.

## Detailed User and Runtime Flows

### Flow A: Enter Plan mode

1. `CollaborationModeToggle` calls Desktop `setCollaborationMode()` with a UUID request ID and `collaborationMode: "plan"`.
2. Preload sends only the typed payload over the dedicated IPC channel; `client-broker.ts` validates it with App Protocol before calling the App Server client.
3. `dispatcher.ts` routes `session/setCollaborationMode` through existing replay protection to the owning runtime host.
4. Runtime host rejects scheduled/subagent sessions, active turns, compaction, and pending interactions before mutation.
5. `AgentSession.setCollaborationMode("plan")` appends the mode control first, preserving a restrictive durable truth if later work is interrupted.
6. AgentSession filters the configured normal tools to the Plan-safe visible set, rebuilds the Plan system prompt, resets the cached Bash boundary, then emits `collaboration_mode_changed`.
7. App Server publishes `session/collaborationModeChanged`; Desktop reducer updates authoritative mode and clears the pending toggle state.
8. No provider request occurs merely because the mode changed.

The UI must disable the toggle during this RPC. Add a renderer-only pending target so a response/event race cannot submit duplicate changes:

```ts
const [pendingCollaborationMode, setPendingCollaborationMode] = useState<CollaborationModeView | null>(null);
```

Set it before the call; clear it on RPC failure or when projection state equals the requested mode. While it is non-null, disable the mode control.

### Flow B: Explore safely in Plan

1. The user sends an ordinary message; no special Plan request method is needed.
2. Immediately before the provider call, AgentSession supplies the Plan-specific system prompt and only the current Plan-visible tool definitions.
3. The model may call structured reads, controlled web/image tools when configured, trusted `ask_user`, or read-only Bash.
4. Bash is classified before execution. Sensitive/opaque/network/elevated/destructive/external-side-effect commands fail immediately.
5. A remaining harmless Bash command receives a one-action `sandbox` binding. The sandbox reads workspace roots, writes only Metis work/temp roots, and cannot write project roots.
6. A write attempt such as shell redirection may pass harmless-command classification but fails at the read-only filesystem mount; it never retries on the host.
7. `ask_user` uses the existing pending-interaction loop. The mode and tool boundary remain Plan while the model waits for and receives the answer.
8. If sandbox initialization fails, return a Bash tool error. Do not remove the Plan restriction or substitute host execution.

### Flow C: Submit the first proposal

1. The model calls `submit_plan({ title, markdown })`; ordinary assistant text is not authoritative Plan content.
2. The trusted tool validates strict shape, trimmed nonblank values, title controls/length, and Markdown UTF-8 bytes.
3. `AgentSession.submitPlan()` verifies current collaboration mode is Plan.
4. With no current proposal, SessionManager generates a new `planId`, sets revision 1, and appends one complete `session_plan_proposal` control attached to the current transcript leaf.
5. SessionManager reduces the journal and returns the stored proposal, not the raw control payload.
6. AgentSession emits `plan_changed` with the proposal entry ID.
7. Runtime host re-reduces branch-visible Plan state and projects that proposal entry to an assistant `ItemView` whose stable `itemId` is the proposal control entry ID.
8. App Server publishes the existing `item/completed` event. Desktop upserts the item and `Transcript` renders exactly one Plan card block.
9. Raw assistant `submit_plan` calls and their tool results are suppressed from App Server item projection so no duplicate tool card appears.
10. The turn may finish with ordinary assistant text, but only the structured Plan block is rendered inside the Plan card.

### Flow D: Revise a proposal

1. Revise performs no Plan mutation. It stores the current `PlanView` as renderer-only `planRevisionTarget`, renders a removable composer chip, and focuses the existing input.
2. The user types ordinary free-form feedback and sends it through the normal prompt path.
3. Before the provider call, `projectPlanContext()` removes all historical `submit_plan` calls/results and injects one hidden JSON custom message containing the current proposal.
4. The Plan system prompt tells the model that `submit_plan` is a complete replacement. The user's feedback remains unmodified text next to the injected exact proposal.
5. A successful next `submit_plan` reuses the current `planId` and writes `revision + 1` with the complete new Markdown.
6. Reduction derives the old proposal as `superseded` and the new one as `proposed`.
7. `plan_changed` includes both proposal entry IDs; App Server emits replacement `item/completed` events for the old card and the new card.
8. Desktop upserts by stable item ID, leaving revision history visible while enabling actions only on the new proposed revision.
9. Clear the revision chip after the user's feedback message is successfully accepted, on manual chip removal, Start, Cancel, session switch, or when projection marks that exact revision non-proposed.
10. If the model does not call `submit_plan`, no revision is fabricated. The current proposal remains proposed and the user may send another Plan-mode instruction.

### Flow E: Open a proposal

1. Open is local renderer behavior and never calls the provider or mutates Plan state.
2. `App.tsx` sets `planPreviewRequest` to the exact `PlanView` and opens the existing tools sidebar.
3. `ToolsSidebar` uses `planId` as tab identity. Opening a later revision updates/focuses that tab instead of adding duplicates.
4. `PlanPreview` renders the complete Markdown with the existing renderer and normal sidebar scrolling/closing/resizing behavior.
5. Superseded, accepted, and cancelled cards remain openable.

### Flow F: Cancel a proposal

1. The card sends its exact `{ planId, revision }`; it never asks App Server to infer the latest revision.
2. Desktop sets `pendingPlanAction` before RPC and disables all Plan mutations.
3. App Server rejects non-primary, busy, pending-interaction, missing, non-current, or non-proposed targets before mutation.
4. AgentSession appends `session_plan_status(cancelled)` before switching mode. This ordering prevents normal tools from becoming available while the plan is still proposed.
5. AgentSession emits the cancelled proposal's `plan_changed`, changes collaboration mode to Default, reapplies normal configured tools/prompt, resets Bash, and emits the mode event.
6. App Server publishes the updated Plan item and mode event; Desktop clears pending state from authoritative projection.
7. Cancel does not submit a prompt and must not increase provider request count.

### Flow G: Start exact-plan execution

1. The card sends its exact `{ planId, revision }` to `plan/startExecution`; Desktop marks that exact action pending.
2. App Server validates session class, idle state, pending interactions, and that the reference is the current proposed revision.
3. Runtime host calls the existing durable prompt path with synthetic text `Execute the accepted plan.` plus `planExecution: { planId, revision }` under the same request ID.
4. `prepareDurablePrompt()` validates the exact current proposal before accepting the operation, so a stale click cannot create a user turn or provider request.
5. The accepted durable operation persists the `planExecution` reference. It is part of canonical request hashing, making reuse of the same request ID with a different revision invalid.
6. At the beginning of `runAcceptedDurablePrompt()`, resolve the exact proposal. Append `accepted` first unless recovery already sees that exact status.
7. Persist mode `default`, reset the Bash boundary, restore configured normal tools and the non-Plan prompt, and emit Plan/mode projection changes before provider work.
8. During this durable operation only, `_currentDurablePlanExecution()` resolves the exact accepted proposal. `projectPlanContext()` gives execution context priority and injects that revision once.
9. The provider sees Default tools including normal write tools and `set_tasks`, does not see `submit_plan`, and receives neither older revisions nor historical `submit_plan` plumbing.
10. When the durable execution scope ends, the injected Plan context disappears automatically. A later ordinary Default turn receives no Plan context.
11. If provider execution fails, the plan remains accepted and auditable; do not roll it back to proposed. The normal interrupted-turn/retry UX owns recovery.

The synthetic execution instruction is expected to appear as the normal user turn that begins implementation. Do not add a second hidden-turn mechanism in this MVP.

### Flow H: Return to Default without a proposal

1. The user may toggle Plan off only when `currentPlan` is absent.
2. App Server rejects direct mode-off while a proposal is current; Start or Cancel must resolve it explicitly.
3. Mode-off persists `session_collaboration_mode(default)`, restores the configured baseline tools, rebuilds the normal prompt, resets the Bash boundary, and publishes the mode event.
4. Because configured tools were stored separately from Plan-visible tools, registry reloads performed during Plan cannot permanently delete normal tools.

### Flow I: Restart, reconnect, and durable recovery

1. SessionManager loads the JSONL, migrates an ordinary valid v11 journal to v12, rejects any pre-v12 journal that already contains Plan controls, and strictly parses Plan controls.
2. `reducePlanState()` reconstructs collaboration mode, revisions, terminal states, and the active branch's current proposal without relying on renderer state.
3. Runtime host projects Plan entries into the initial `SessionProjection`; snapshots contain collaboration mode plus ordinary Plan item blocks.
4. Snapshot/reconnect pages use both count and 6 MiB serialized-item limits so valid revision history cannot exceed the 8 MiB envelope.
5. Desktop replaces its projection from the snapshot; no Plan-specific local persistence is read.
6. An incomplete accepted durable execution may replay with the exact proposal already marked accepted. The runtime transition must treat that status as idempotent, avoid a duplicate status record, restore Default tools, and continue the admitted operation.

## Provider Context and Tool Projection Algorithms

### Provider context order

Install hooks in this order and preserve the chaining semantics:

```text
session transcript context
  -> subagent mailbox hook (existing)
  -> Plan context hook (new: strip submit_plan history, select zero/one Plan)
  -> tool-result microcompaction hook (existing)
  -> provider serialization
```

`projectPlanContext()` must be a pure function with these exact outcomes:

| Collaboration/execution input | Hidden Plan message |
|---|---|
| Default, no durable execution scope | None. |
| Plan, no current proposal | None. |
| Plan, current proposed revision | Exactly that current revision. |
| Any mode, active durable `planExecution` | Exactly the referenced accepted revision; this wins over current proposal selection. |

In every case, remove historical assistant `submit_plan` tool-call blocks and matching tool-result messages first. Preserve unrelated content from mixed assistant messages. Never mutate persisted messages while projecting.

### Visible tool calculation

```text
configuredActiveToolNames
  -> refresh registry while preserving configured names
  -> overlay exact trusted ask_user/submit_plan definitions after untrusted names
  -> if Default: visible = configured names present in registry
  -> if Plan: visible = trusted safe intersection + trusted submit_plan
  -> rebuild tool schema and system prompt from visible names
```

An absent optional safe tool stays absent. For example, Plan does not enable `web_search` when the user disabled it. An untrusted extension/MCP tool named `submit_plan`, `ask_user`, `read`, or `bash` must not pass the provenance check.

### Plan Bash decision path

| Stage | Decision |
|---|---|
| Tool visibility | Only the exact built-in Bash definition may be visible. |
| Classifier | Always classify the effective command before execution. |
| Risk gate | Deny sensitive-read, unknown, network, elevation, destructive, and external-side-effect risks. |
| Execution target | Bind every remaining Plan Bash action to `sandbox`; never request or retain a host binding. |
| Mount policy | Workspace roots are readable but omitted from allowed writes; Metis work/temp roots remain writable. |
| Runtime failure | Return a tool error and fail closed; no host fallback. |
| Mode switch | Reset the cached sandbox generation before resolving the mutation so a writable Default sandbox is not reused. |

## Validation, Ordering, and Failure Invariants

The implementation is incomplete unless these invariants are explicit in code and covered by the named tests:

1. Validate session class, busy/pending state, and exact revision before any card-action mutation.
2. Persist restrictive/terminal state before enabling Default write tools: proposal status first, Default mode second, provider work last.
3. Apply the visible-tool restriction independently of the prompt; a prompt bug must not expose mutating tools.
4. Apply filesystem read-only enforcement independently of Bash classification; an unrecognized write syntax must still fail at the mount.
5. Never turn a sandbox error into host execution.
6. Never derive configured Default tools from the filtered Plan-visible list.
7. Never parse or render arbitrary assistant prose as a Plan card.
8. Never include all durable revisions in provider context.
9. Never create an automatic Markdown Plan file.
10. Use exact `planId` + `revision` for Start/Cancel and request hashing; do not use “latest” after admission.
11. Re-emitting `item/completed` for an existing proposal entry ID replaces the card status without duplicating the item.

```ts
import type { SessionControlEntry } from "./session-control.ts";

export type CollaborationMode = "default" | "plan";
export type PlanStatus = "proposed" | "superseded" | "accepted" | "cancelled";

export const MAX_PLAN_TITLE_UTF16_UNITS = 256;
export const MAX_PLAN_MARKDOWN_UTF8_BYTES = 64 * 1024;

export interface PlanRef {
	readonly planId: string;
	readonly revision: number;
}

export interface StoredPlan {
	readonly entryId: string;
	readonly parentId: string | null;
	readonly planId: string;
	readonly revision: number;
	readonly title: string;
	readonly markdown: string;
	readonly status: PlanStatus;
	readonly createdAt: string;
}

export interface PlanState {
	readonly collaborationMode: CollaborationMode;
	readonly plans: readonly StoredPlan[];
	readonly currentPlan?: StoredPlan;
}

type PlanControlEntry = Extract<
	SessionControlEntry,
	{ type: "session_collaboration_mode" | "session_plan_proposal" | "session_plan_status" }
>;

function isPlanControlEntry(value: unknown): value is PlanControlEntry {
	if (typeof value !== "object" || value === null) return false;
	const type = Reflect.get(value, "type");
	return type === "session_collaboration_mode" || type === "session_plan_proposal" || type === "session_plan_status";
}

export function reducePlanState(entries: readonly unknown[], activeBranchIds?: ReadonlySet<string>): PlanState {
	let collaborationMode: CollaborationMode = "default";
	const proposals: StoredPlan[] = [];
	const terminal = new Map<string, "accepted" | "cancelled">();
	for (const entry of entries) {
		if (!isPlanControlEntry(entry)) continue;
		if (entry.type === "session_collaboration_mode") {
			collaborationMode = entry.collaborationMode;
			continue;
		}
		if (entry.type === "session_plan_status") {
			if (activeBranchIds && entry.parentId !== null && !activeBranchIds.has(entry.parentId)) continue;
			terminal.set(`${entry.planId}:${entry.revision}`, entry.status);
			continue;
		}
		if (entry.type !== "session_plan_proposal") continue;
		if (activeBranchIds && entry.parentId !== null && !activeBranchIds.has(entry.parentId)) continue;
		proposals.push({
			entryId: entry.id,
			parentId: entry.parentId,
			planId: entry.planId,
			revision: entry.revision,
			title: entry.title,
			markdown: entry.markdown,
			status: "proposed",
			createdAt: entry.timestamp,
		});
	}
	const plans = proposals.map((plan, index) => {
		const explicit = terminal.get(`${plan.planId}:${plan.revision}`);
		const superseded = proposals.slice(index + 1).some(
			(candidate) => candidate.planId === plan.planId && candidate.revision > plan.revision,
		);
		return { ...plan, status: explicit ?? (superseded ? "superseded" : "proposed") };
	});
	return { collaborationMode, plans, currentPlan: [...plans].reverse().find((plan) => plan.status === "proposed") };
}
```

```ts
const PLAN_BUILTINS = new Set(["read", "grep", "bash", "web_fetch", "web_search", "describe_image"]);

export function planVisibleToolNames(
	configured: readonly string[],
	source: (name: string) => "builtin" | "trusted" | "extension" | "mcp" | "sdk" | undefined,
): string[] {
	const visible = configured.filter((name) => {
		const provenance = source(name);
		return (PLAN_BUILTINS.has(name) && provenance === "builtin") || (name === "ask_user" && provenance === "trusted");
	});
	if (source("submit_plan") === "trusted") visible.push("submit_plan");
	return [...new Set(visible)];
}
```

```ts
private itemPage(end: number, limit: number): readonly string[] {
```
